What is Git for?#

Git is version control. It keeps your code’s history.

In Lab 03, we saved the seed and inputs. We need the code that used them too.

  • Commit: a snapshot you choose to record, with a message, author, and links to earlier commits.

  • Compare: see what changed and where a problem started.

  • Recover: get back to work you’ve committed.

  • Branch and merge: try changes separately, then combine them.

  • Work offline: a normal clone includes the files and history. Git is distributed.

Keep one project with a history, instead of simulation_final.py, simulation_final2.py, and simulation_really_final.py.

  • For a result, record commit + seed + inputs + environment.

  • Save, commit, and push are separate steps.

  • Still check the physics. Git doesn’t tell us whether the calculation is right.

What does GitHub add?#

GitHub hosts Git repositories online. Git works without it.

Git

GitHub

Keeps commits and branches

Hosts the code and history

Compares and combines changes

Adds sharing, permissions, and review

Works locally, including offline

Lets others access the work online

  • Pull requests: propose and review changes.

  • Issues: track problems and work to do.

  • Forks: make your own repository from someone else’s; contribute back if you want.

  • Actions: run automated checks.

Here, local means the machine running Git: DataHub or your laptop. DataHub runs on a server; GitHub holds another copy.

Set up SSH before cloning your fork#

Create an SSH key#

Your public key goes on GitHub. Your private key stays here.

Run this on the machine where you run Git: DataHub for this lab.

mkdir -p ~/.ssh
chmod 700 ~/.ssh
ls -la ~/.ssh

  • Already see id_ed25519_phys142 or id_ed25519_phys142.pub? Don’t overwrite them. Ask me.

  • Otherwise, replace YOUR-GITHUB-EMAIL below and create the key:

ssh-keygen -t ed25519 -C "YOUR-GITHUB-EMAIL" -f ~/.ssh/id_ed25519_phys142

  • Enter a passphrase at the prompts. It protects the private key; it isn’t your GitHub password.

  • id_ed25519_phys142 is private. Don’t share it or put it in a repo.

  • id_ed25519_phys142.pub is public. That’s the one we’ll copy to GitHub.

Load the key into an agent in this terminal:

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519_phys142
ssh-add -l

  • ssh-add asks for the key’s passphrase. ssh-add -l should list the key.

  • After a new terminal or DataHub restart, rerun the agent block. Don’t generate another key.

More: SSH keys and the agent

Add the public key to GitHub#

cat ~/.ssh/id_ed25519_phys142.pub

  1. Copy the whole line, starting with ssh-ed25519.

  2. Open GitHub Settings → SSH and GPG keys → New SSH key.

  3. Title: PHYS 142 DataHub. Key type: Authentication Key.

  4. Paste the public key and choose Add SSH key.

Test the connection using this key:

ssh -T -i ~/.ssh/id_ed25519_phys142 -o IdentitiesOnly=yes git@github.com

  • First connection? Compare the displayed fingerprint with GitHub’s published fingerprints. Type yes only if it matches.

  • The greeting must name your GitHub account. If it names someone else or says Permission denied, stop and ask me.

  • Successfully authenticated plus does not provide shell access is success. GitHub accepts Git operations, not an interactive shell; this test normally exits with status 1.

  • git@github.com always uses the SSH user git. The key identifies your GitHub account.

Pro Git: branching and merging.

Push your work and bring updates back#

Upload the committed history#

  • Push. Then check GitHub.

  • Run the first two commands. Check your fork’s URL and main before pushing.

git remote -v
git branch --show-current
git push origin main
git rev-parse --short HEAD
git status

  • We’ve pushed main and its history, including the merged work.

  • This doesn’t push every local branch name.

Refresh main on GitHub and check:

  1. homework/practice/settings.txt has 1000 samples.

  2. homework/practice/NOTES.md is there.

  3. The latest commit ID matches the local HEAD printed above.

Make a remote change, then update the clone#

  • Change it on GitHub. Check your local copy.

  1. On GitHub, open homework/README.md in your fork, on main.

  2. Add Current practice sample count: 1000. and commit directly to main.

  3. Our local copy is still on the earlier commit. Fetch and compare:

git status
git fetch origin
git log --oneline main..origin/main
git diff main origin/main -- homework/README.md
cat homework/README.md

  • origin/main is our local record of the fork’s branch after fetching. It doesn’t watch GitHub for updates.

  • Log and diff show the new commit; cat homework/README.md still shows the old file.

  • Check that the working tree is clean, then bring the commit into our main:

git merge --ff-only origin/main
cat homework/README.md
git status

  • Next time: git pull --ff-only origin main combines fetch and fast-forward.

  • No second commit needed. We brought in the existing one.

  • --ff-only stops if the local and remote histories have diverged.

  • If it stops, run git log --oneline --graph --all --decorate and show me. We’ll look at the histories before combining them.

  • Don’t force-push or discard local work to get past the error.

Fetch from the course. Merge locally. Push to your fork.

New material appears in jmduarte/phys142. Your fork doesn’t update itself.

  1. Work in ~/phys142-lab04/phys142.

  2. Save your files. Check for a clean working tree; commit work you want to keep before switching or merging.

  3. Update from your fork, then check the course:

git status
git switch main
git pull --ff-only origin main
git fetch upstream
git log --oneline main..upstream/main

Command

What it does

pull --ff-only origin main

Brings in changes from your GitHub fork

fetch upstream

Downloads course history; leaves working files alone

log main..upstream/main

Lists course commits your main doesn’t have

upstream/main is our local record after the fetch. An empty log means no new course commits.

  1. Merge the course history into main, then push to your fork:

git merge --no-edit upstream/main
git log --oneline --graph --all --decorate -10
git push origin main
git status

  • Already up to date? Nothing new to merge. Repeat when new material is posted.

  • Both sides have new commits? Git may make a merge commit keeping both histories.

  • No --ff-only on this merge: your homework can make the histories diverge.

  • --no-edit accepts Git’s generated merge message.

  • Conflict? Look at the files with me; the optional exercise below covers this. Don’t force-push or discard work.

origin is your fork. Pulling from it alone won’t fetch course updates. After fetching upstream, you still need to merge, then push.

Optional: make and resolve a merge conflict#

  • A conflict can occur when two branches change the same line incompatibly.

  • Use two local branches. Leave main unchanged; don’t push these branches.

  • Stay in ~/phys142-lab04/phys142. Check that git status is clean.

  1. Create the first branch:

git switch main
git switch -c seed-a

  1. In homework/practice/settings.txt, replace seed = 20261008 with seed = 11. Save, then:

git add homework/practice/settings.txt
git commit -m "Try seed 11"
git switch main
git switch -c seed-b

  1. seed-b starts from main, where the seed is still 20261008. In the same file, replace it with seed = 22, save, then:

git add homework/practice/settings.txt
git commit -m "Try seed 22"
git merge seed-a

The merge should stop with a conflict in homework/practice/settings.txt: both branches changed the same seed. We must choose what to keep.

Resolve, inspect, then commit#

Keep seed 11. The complete file should be:

distribution = fair_die
seed = 11
samples = 1000

Save, then inspect and commit:

git diff
git add homework/practice/settings.txt
git diff --staged
git commit -m "Resolve the seed conflict using seed 11"
git status
git log --oneline --graph --all --decorate -10
git switch main
cat homework/practice/settings.txt

  • Back on main, the seed should still be 20261008. The merge commit is on seed-b.

  • In a real simulation, changing the seed can change the result. Rerun the calculation and record the seed.

  • To cancel a conflicted merge, run git merge --abort before resolving and committing. Because we started clean, this restores the pre-merge state. It doesn’t undo a committed merge.

When something stops you#

What you see

What to check

not a git repository

Run pwd; enter the clone, not its parent directory.

Author identity unknown

Set user.name and user.email inside the repository.

nothing to commit

Save your file, then check git status. Did you already commit the change?

Permission denied (publickey) when cloning, fetching, or pushing your fork

Check your fork’s SSH URL, ssh-add -l, and that the public key is on your GitHub account. Repeat the connection test above.

No connection to the authentication agent

Rerun the ssh-agent and ssh-add block in this terminal.

Push rejected as non-fast-forward

The remote has history your branch doesn’t contain. Fetch, look at the graph, and show me before combining the changes.

Switching or merging would overwrite local changes

Look at the changes and commit the work you want to keep before switching. Don’t discard it just to get past the error.

Conflict markers in a file

Resolve the content, remove markers, stage, inspect, and complete the merge.

  • Save notebooks before staging. Outputs and metadata can make diffs large; clear outputs you don’t need.

  • Agree on who edits each notebook. Move frequently shared code into small text modules to make changes easier to compare and merge.

  • GitHub’s notebook preview displays the file; it doesn’t run the Python code.
